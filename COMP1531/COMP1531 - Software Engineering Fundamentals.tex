	\section{Introduction to Software Engineering}

		What is the difference between Computer Science and Software Engineering.

		\begin{itemize}
			\item Computer science focuses on understanding how computers work and function
			\item Software engineering is about creating software for people to use, and building software that is maintainable over time
		\end{itemize}

		The Software Development Life Cycle is a structured approach to software development that includes:

			\begin{itemize}
				\item Requirements analysis
					\begin{itemize}
						\item Talk to potential clients
						\item Work out what is needed of the software
					\end{itemize}
				\item Design
					\begin{itemize}
						\item Designing an outline for the software
					\end{itemize}
				\item Development
					\begin{itemize}
						\item Writing the actual code to handle the task
					\end{itemize}
				\item Testing
					\begin{itemize}
						\item Test the program to see if it meets the initial requirements
					\end{itemize}
				\item Deployment
					\begin{itemize}
						\item Deploy the software to users
					\end{itemize}
				\item Maintenance
					\begin{itemize}
						\item Continue to develop, fixing bugs and implementing new features
					\end{itemize}
			\end{itemize}
		
		Software quality and productivity is supported by three key pillars: people, technology, and processes.

\chapter{Importing Libraries}
	
	Libraries allow us to use code that other people have written in our own projects. In JavaScript, we can do so by adding the header \mintinline{js}{import fs from 'fs'}. Unlike C, the functions that are important can not be directly called. Instead, the functions exist as methods on objects, where the object name is specified when the library is imported.
	\\ \\
	We can also import our own code in other files. The functions that we want to use elsewhere can be exported by adding \mintinline{js}{export} or \mintinline{js}{export default}. The \mintinline{js}{default} keyword means that when the function is imported it will run the defaulted command. This is useful when providing an alias for the function.
	\\ \\
	Functions from other people can be downloaded into our directory using npm. Running npm init will create a package.json that has the information required modules to tell other people what to install. Installed packages are added to the node\_modules folder. This folder is gitignored to save space.

\chapter{Software Complexity}

	\begin{itemize}
		\item Essential
			\begin{itemize}
				\item Complexity that is inherent to the problem
				\item Eg.\ if the user or client requires the program to do 30 different things, then those 30 things are essential
			\end{itemize}
		\item Accidental
			\begin{itemize}
				\item Complexity that is not inherent to the problem
				\item Eg.\ generating or parsing data in specific formats
			\end{itemize}
		\item Coupling
			\begin{itemize}
				\item A measure of how closely connected different software components are
				\item Usually expressed as a simple ordinal measure of `loose' or `tight'
				\item Eg.\ web applications tend to have a front-end that is loosely coupled from the backend
				\item Loose coupling is good
			\end{itemize}
		\item Cohesion
			\begin{itemize}
				\item The degree to which elements of a module belong together
				\item Elements belong together if they are somehow related
				\item High cohesion is good
			\end{itemize}
		\item Cyclomatic complexity
			\begin{itemize}
				\item A measure of the branching complexity of functions
				\item Computed by counting the number of linearly-independent paths through a function
				\item Convert function into a control flow graph
					\begin{align*}
						V(G) = e - n + 2
					\end{align*}
					where $e$ is the number of edges and $n$ is the number of nodes.
				\item Low cyclomatic complexity is better
			\end{itemize}
	\end{itemize}

\chapter{Agile Software Engineering}

	\begin{itemize}
		\item What is agile?
			\begin{itemize}
				\item Agile is a software development philosophy that focuses on delivering valuable software through small, frequent releases rather than one large release at the end of a project
				\item Unlike traditional approaches, Agile assumes that requirements will change as customers learn more about their needs
				\item The goal is not simply writing code, but continuously delivering value to users
			\end{itemize}
			\begin{itemize}
				\item In 1990s many software projects failed because teams spent months gathering requirements, writing documentation, and producing detailed designs before writing code
				\item Customer needs changed
				\item Competitors released better products faster
			\end{itemize}
		\item Agile practices
			\begin{itemize}
				\item Build small pieces of working software
				\item Release frequently
				\item Gather customer feedback early
				\item Adapt to changing requirements
				\item Continuously improve the product
			\end{itemize}
			\begin{enumerate}
				\item Satisfy customers through early delivery
				\item Welcome changing requirements
				\item Deliver software frequently
				\item Developers and customers work together
				\item Build projects around motivated people
				\item Face-to-face conversations are the most effective way to share information
				\item Working software is the primary measure of progress
				\item Maintain sustainable development
				\item Pursue technical excellence
				\item Keep solutions simple
			\end{enumerate}
			\begin{itemize}
				\item \textbf{Key Agile Values}
					\begin{itemize}
						\item Individuals and interactions over processes and tools
						\item Working software over comprehensive documentation
						\item Customer collaboration over contract negotiation
						\item Responding to change over following a plan
					\end{itemize}
				\item Successful Agile teams commonly use
					\begin{itemize}
						\item User stories
						\item Test driven development
					\end{itemize}
			\end{itemize}
		\item Why agile works
			\begin{itemize}
				\item Agile succeeds because it shortens the feedback loop
				\item Fast feedback means fewer mistakes
			\end{itemize}
		\item Some examples
	\end{itemize}
